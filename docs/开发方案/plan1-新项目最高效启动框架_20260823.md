## 目标判断

当前思路是正确的：新项目第一步不应该把 Agent、Skill、Workflow、Postgres、平台写入全部铺满，而应该先做一个最小闭环。

第一版主线保持简单：

| 判断 | 结论 |
| --- | --- |
| 产品形态 | 左侧对话入口 + 右侧 Workflow 看板 |
| 第一版 Agent | 只做投放创建 Agent |
| 第一版路线 | `oceanengine_3_byte_mini_game` |
| 第一版创建对象 | `std_project` |
| 第一版核心目标 | 跑通一个账户、一款游戏、一条路线的创建准备流程 |
| 暂不做 | 多平台、多 Agent、复杂推荐、真实平台写入自动化 |

最重要的原则是：先让页面、API、数据库和 Workflow 状态形成闭环，再逐步接入真实平台能力。

## 三阶段推进

| 阶段 | 目标 | 关键动作 | 不做什么 |
| --- | --- | --- | --- |
| 阶段 1：项目骨架与前端外壳 | 让新项目可以被 Codex 稳定协作，并看到前端页面 | 建 `AGENTS.md`、`project.state.json`、`tasks/`、`tasks-context-manifests/`；完成左侧对话 + 右侧 3 阶段 7 节点页面外壳 | 不接真实数据库，不做真实创建 |
| 阶段 2：Postgres 最小真值 | 让一个账户、一款游戏、一条路线能被结构化读取 | 建最小表；填入一组账户、游戏、路线、素材包和节点状态样例 | 不追求多账户、多路线、多平台兼容 |
| 阶段 3：前后端流程闭环 | 让页面、API、Workflow、Postgres 可以串起来跑 | 跑通 `Intake -> job -> 7 节点 -> 诊断 -> 草稿 -> 确认占位 -> 回查占位` | 不做真实投放写入，不刷新凭据 |

### 阶段 1：项目骨架与前端外壳

第一阶段只需要把协作入口和页面外壳立起来。

必备文件和目录：

```text
marketing-workbench-v2/
├── AGENTS.md
├── project.state.json
├── package.json
├── docs/
├── tasks/
├── tasks-context-manifests/
├── frontend/
└── src/
    └── server/
```

前端外壳只需要表达清楚工作台形态：

| 区域 | 第一版内容 |
| --- | --- |
| 左侧 | 对话入口、需求输入框、LLM 配置入口占位、Agent 状态 |
| 右侧 | `准备阶段`、`就绪阶段`、`创建执行` |
| Workflow | 7 个节点状态卡 |
| 诊断 | 节点卡点、缺口、下一步动作 |
| 草稿 | 创建草稿占位，不展示敏感原文 |

7 个节点固定为：

| 阶段 | 节点 |
| --- | --- |
| 准备阶段 | 1. Intake 规范 |
| 准备阶段 | 2. 创建上下文装配 |
| 准备阶段 | 3. 游戏保底包解析 |
| 就绪阶段 | 4. 账户资源诊断与补齐 |
| 就绪阶段 | 5. 创建草稿生成 |
| 创建执行 | 6. 创建执行 |
| 创建执行 | 7. 回查收口 |

### 阶段 2：Postgres 最小真值

第二阶段单独开一个任务，只建够最小闭环需要的表，并填一组可跑通样例数据。

最小表：

| 表 | 第一版用途 |
| --- | --- |
| `platform_routes` | 保存 `oceanengine_3_byte_mini_game` 路线、版本、创建对象和写入策略 |
| `games` | 保存一款游戏的主档信息 |
| `advertiser_accounts` | 保存一个广告账户的基础状态 |
| `account_touchpoints` | 保存监测序号、触点引用、链接摘要和解析状态 |
| `game_route_defaults` | 保存游戏 x 路线的预算、出价、优化目标、排期等默认值 |
| `game_assets` | 保存游戏产品图、头像、视频、小游戏资产等引用 |
| `material_packs` | 保存游戏保底物料包 |
| `material_pack_items` | 保存保底物料包明细 |
| `launch_jobs` | 保存一次投放创建任务 |
| `launch_node_runs` | 保存 7 个节点的运行状态 |
| `launch_drafts` | 保存创建草稿、摘要和稳定 hash |
| `readback_records` | 保存回查占位和后续真实回查结果 |
| `evidence_artifacts` | 保存脱敏证据、摘要、hash 和引用 |

样例数据只需要覆盖：

| 类型 | 要求 |
| --- | --- |
| 路线 | 1 条：`oceanengine_3_byte_mini_game` |
| 游戏 | 1 款：有 `game_slug`、游戏名、产品名、品类 |
| 账户 | 1 个：有 `advertiser_id`、授权状态、平台状态 |
| 素材 | 1 个保底包：能支撑页面展示和草稿生成 |
| Workflow | 1 个 job：初始化 7 个节点 |

### 阶段 3：前后端流程闭环

第三阶段先跑通应用闭环，不急着接真实写入。

最小 API：

| 接口 | 用途 |
| --- | --- |
| `POST /api/launch/intake` | 解析自然语言，返回 `route_id`、`game_slug`、`advertiser_id` 和缺参 |
| `POST /api/launch/jobs` | 创建任务，并初始化 7 个节点 |
| `GET /api/launch/jobs/:job_id` | 返回页面所需的任务摘要、节点状态、诊断和草稿 |
| `POST /api/launch/jobs/:job_id/diagnose` | 运行诊断，更新节点状态 |
| `POST /api/launch/jobs/:job_id/run` | 从当前节点继续执行 |
| `POST /api/launch/jobs/:job_id/confirm` | 确认草稿，占位记录确认状态 |
| `POST /api/launch/jobs/:job_id/readback` | 触发回查占位，生成收口状态 |

最小流程：

```text
用户输入
  -> Intake 规范
  -> 创建 launch_job
  -> 初始化 7 个 launch_node_runs
  -> 读取 Postgres 最小真值
  -> 生成诊断报告
  -> 生成创建草稿
  -> 记录确认占位
  -> 记录回查占位
  -> 页面刷新展示闭环结果
```

## 最高效目录框架

第一版目录应该少而清楚，先保留扩展位置，不提前铺满复杂实现。

```text
marketing-workbench-v2/
├── AGENTS.md
├── project.state.json
├── package.json
├── docs/
├── tasks/
├── tasks-context-manifests/
├── frontend/
├── src/
│   ├── server/
│   ├── agents/
│   ├── workflows/
│   ├── repositories/
│   └── platforms/
├── db/
├── schemas/
├── scripts/
├── tests/
└── .local/
```

目录职责：

| 目录 | 职责 | 第一版建议 |
| --- | --- | --- |
| `AGENTS.md` | Codex 协作协议和安全红线 | 先写启动顺序、真值优先级、禁止真实平台写入 |
| `project.state.json` | 当前项目状态、活动任务和下一步 gate | 初始保持 `active_task = null`，新任务开始后再挂任务卡 |
| `docs/` | 稳定说明文档 | 保存启动框架、投放创建方案、API、数据库说明 |
| `tasks/` | 单个开发任务合同 | 阶段 1、阶段 2、阶段 3 分别建任务 |
| `tasks-context-manifests/` | 任务上下文清单 | 记录每个任务必读文件和排除项 |
| `frontend/` | 页面外壳和交互 | 先做左侧对话 + 右侧 Workflow 看板 |
| `src/server/` | 本地 API 服务 | 提供 launch API 和页面数据读取 |
| `src/agents/` | Agent 主控入口 | 第一版只放投放创建 Agent |
| `src/workflows/` | 7 节点 Workflow 编排 | 先实现状态流转和诊断，不接真实写入 |
| `src/repositories/` | Postgres 读写封装 | 统一读写最小真值表 |
| `src/platforms/` | 平台适配位置 | 第一版只放 OceanEngine 占位和只读能力 |
| `db/` | 数据库 migration 和 seed | 阶段 2 再建立 |
| `schemas/` | API、Workflow、草稿、证据结构 | 先保证前后端契约稳定 |
| `scripts/` | 本地开发、seed、smoke、诊断脚本 | 先放启动和 smoke，真实写入脚本后置 |
| `tests/` | 单测、契约测试、smoke | 先测 API 和页面闭环 |
| `.local/` | 本机私密配置 | 不进入版本管理 |

## 每阶段验收标准

| 阶段 | 验收标准 |
| --- | --- |
| 阶段 1 | 打开前端页面后，能看到左侧对话入口、右侧 3 阶段 7 节点、诊断区域和草稿占位 |
| 阶段 1 | `AGENTS.md`、`project.state.json`、`tasks/`、`tasks-context-manifests/` 已存在，并能说明 Codex 如何接任务 |
| 阶段 2 | Postgres 中存在最小表，并能查询到一个账户、一款游戏、一条路线和一个初始化 job |
| 阶段 2 | 前端可以从后端读取 Postgres 数据，而不是只依赖 hardcoded mock |
| 阶段 3 | 用户输入需求后，可以创建 job，并在页面看到 7 个节点状态变化 |
| 阶段 3 | 诊断报告能指出缺口、通过项和下一步动作 |
| 阶段 3 | 创建草稿能生成稳定 hash 和确认占位 |
| 阶段 3 | 回查收口可以生成占位结果，并归档脱敏证据 |

## 后续扩展边界

第一版完成前，以下能力暂缓：

| 能力 | 暂缓原因 | 后续接入时机 |
| --- | --- | --- |
| 真实平台写入 | 需要更严格的确认、审计、幂等和回查机制 | 阶段 3 闭环稳定后，单独开 write-once 任务 |
| 素材策略 Agent | 会引入素材推荐、策略评价和多轮选择复杂度 | 投放创建闭环稳定后 |
| 归因分析 Agent | 属于投后分析，不影响第一版创建准备流程 | 有真实创建和回查记录后 |
| 经验检索 Agent | 需要成功路径沉淀和检索索引 | 至少有多次可验证成功样本后 |
| 多平台/多路线 | 会放大配置、adapter、schema 和测试范围 | 单路线稳定后再扩展 |
| 自动预算/出价决策 | 涉及高风险业务动作 | 只在人类确认策略后推进 |

安全边界：

| 边界 | 要求 |
| --- | --- |
| 平台写入 | 第一版默认禁止真实写入 |
| 凭据 | 只进入本机私密配置，不写入文档、源码、日志和普通接口响应 |
| 私密链接 | 普通页面和文档只展示引用、摘要和状态 |
| 平台返回 | 普通证据只保存脱敏摘要和 hash |
| 长数字 ID | 一律按字符串处理 |

这份启动框架的最终目的不是一次性设计完所有系统，而是让新项目按最短路径进入可运行状态：先协作骨架，再数据真值，再前后端 Workflow 闭环。

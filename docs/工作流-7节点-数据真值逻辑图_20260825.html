marketing-workbench-v2：7 节点 Workflow 与 Postgres 真值逻辑图

范围：当前第一版 oceanengine_3_byte_mini_game 路线与 std_project。这是“通用工作台骨架 + OE3 路线 Skill 实现”，不是已经支持所有媒体平台的通用编排器。

结论先行：7 节点、单次运行包、Skill 日志、草稿 hash 与平台写入边界的分层是清晰的。最重要的真值入口是 mwb.launch_jobs 的一轮任务，Repository 将维度事实一次装配为 bundle，Skill 只消费 bundle 并写入可审计摘要。

三、Postgres 真值分层

维度事实：可复用的输入

路线与游戏
  • platform_routes：route_id、platform、marketing_product、object_type
  • games：game_code、产品、品类、品牌
  • game_platform_apps：平台 + app 类型 → app_id
策略与物料
  • game_route_defaults：目标、预算、出价、raw_defaults
  • material_packs / material_pack_items
  • game_assets：视频、产品图、身份等 metadata

单轮 bundle：唯一装配点

由 getLaunchJobBundle(jobId) 以 launch_jobs 为锚点聚合。Workflow 不应散落地自行查询业务表。

  • job：当前轮次与三元组
  • route / game / account
  • touchpoint / defaults / platformApp
  • materialPack.items[]
  • resources[]
  • nodes / draft / platformAction / readback
→

运行与审计：每轮输出

  • launch_jobs：轮次状态
  • launch_node_runs：7 节点结果
  • launch_skill_runs：细粒度 Skill
  • launch_drafts：摘要 + hash，非 raw payload
  • launch_confirmations / platform_actions / created_objects
  • readback_records / evidence_artifacts

五、当前是否“通用且最简洁”

已经正确的部分

  1. 一轮任务以 launch_jobs 为锚点，运行记录不再依赖文件夹。
  2. Repository 聚合 bundle，避免 Skill 到处拼 SQL。
  3. 节点状态与 Skill 状态分表，既保持工作台简洁，也能定位最小故障单元。
  4. raw payload 与受控触点不落普通记录，只保留 hash 与摘要。

应保持警觉的三点

  1. launchWorkflow.mjs 与 runner.mjs 各自维护 7 节点定义，存在双写漂移风险；应以后者或独立 definition 模块为唯一来源。
  2. 当前 runner 以 if/else 分发 OE3 Skill，第一版可读，但它并非多平台通用注册器。
  3. 物料包按“当前最新 active/baseline”装配；关键创建轮次最好在草稿摘要中固化实际 pack_id 与资源版本，防止运行期间基准包变化。

现在不必提前做的事

  1. 不必为了未来平台先搭通用 DAG 引擎或插件系统。
  2. 不必把 account_resources.metadata 立即拆成多张资源表；现阶段只需为重要 JSONB shape 配 schema/test。
  3. 不必让前端理解 Skill；前端只读节点摘要、进度、阻断与一次确认状态。

# 新账户一键创建：工作流 7 节点与数据真值说明

更新时间：2026-08-27 CST

用途：定义市场推广工作台面向新账户的目标运行逻辑。用户完成对话后只点击一次“开始执行”；系统自动完成上下文、monitor、资源、草稿、单次创建与回查。本文是目标态设计说明，不代表当前已全部实现。

当前实现注记：

- `launch_execution_plans` 与 `planned_actions` 基础已落地。
- Node 2 `ensure_monitor` 已可在 `planned_actions` mock 模式接入主 Workflow，并写入 monitor provision run/attempt、账户、触点、Skill run 和 evidence 摘要。
- 真实乾坤 monitor 创建、资源真实准备和 `std_project/create` 仍未自动化放开，必须按 `project.state.json.guardrails` 另行单次授权。

## 1. 核心原则

- 用户输入并确认 `route_id`、`game_code`、`advertiser_id` 后，只需点击一次“开始执行”。
- 新账户缺少 `monitor_id` 时，Node 2 自动完成 monitor 创建、回查和触点写回，不要求人工另开流程。
- 每个可视子节点对应独立 `skill_key`，拥有固定输入、输出、停止条件、代码入口和写入范围。
- 前端不重新判断业务就绪性；主节点和子节点状态只读取后端写入 Postgres 的运行结果。
- 每个真实平台动作都有独立幂等键、最多一次的动作边界和回查；`std_project/create` 不自动重试。
- token、Cookie、完整 URL、raw request、raw response 不进入普通表、API、前端或本说明。

## 2. 新账户一键创建逻辑

```text
用户对话
  输入：route_id + game_code + advertiser_id
        |
        v
创建 launch_job
  初始化 7 个主节点和全部子节点为 waiting
  工作台按钮全部显示灰色
        |
        v
用户点击一次“开始执行”
        |
        v
生成 launch_execution_plan
  仅列出本轮明确需要的动作：
  - ensure_monitor（仅缺 monitor 时）
  - ensure_resource:*（仅资源缺失且可自动补齐时）
  - std_project_create
        |
        v
生成 execution_grant
  绑定：job_id + execution_plan_hash + action allowlist
  - 用户只确认一次
  - 每个 action_type 最多真实执行一次
  - monitor 忙碌时等待 5 秒，最多尝试 2 次
  - std_project/create 禁止自动重试
  - 运行中不得临时增加真实写入动作
        |
        v
01 Intake 规范
  归一并校验路线、游戏、账户
        |
        v
02 创建上下文装配
  账户 -> monitor 查询 -> 缺失则 monitor 创建与回查
  -> 触点解析与校验 -> 字节小游戏 App 解析
        |
        v
03 游戏保底包解析
  游戏产品 -> 品牌类目 -> 投放目标 -> 预算排期
  -> DMP -> 素材包 -> 备用落地页
        |
        v
04 账户资源准备
  目标账户只读核验 -> 缺失时执行计划内最小准备动作 -> 平台回查
  资源：头像、DMP、事件链、视频、产品图、品牌、小游戏实例、备用落地页
        |
        v
05 创建草稿生成
  项目名 -> 草稿 -> 字段合同 -> 查重 -> payload_hash -> create readiness
        |
        v
06 创建执行
  校验 execution_grant 与最新 payload_hash -> 单次 std_project/create -> 写入 object_id
        |
        v
07 回查收口
  校验对象 ID、状态、名称与关键字段
  成功：readback_verified
  未确认或不一致：stopped，禁止当前 job 再次创建
        |
        v
用户再次发送对话
  创建新的 launch_job；旧 job 只保留审计、诊断和证据
```

## 3. 7 节点与可视子节点

| 节点 | 可视子节点 | 目标 Skill |
| --- | --- | --- |
| 01 Intake | 路线、游戏、账户 | `route_normalize`、`game_normalize`、`advertiser_normalize` |
| 02 创建上下文 | 账户、monitor、触点、平台 App | `account_resolve`、`monitor_query`、`monitor_plan`、`monitor_ensure`、`touchpoint_resolve`、`platform_app_resolve` |
| 03 游戏保底包 | 游戏产品、品牌类目、投放目标、预算排期、DMP、素材包、备用落地页 | `game_product_resolve`、`brand_category_resolve`、`delivery_goal_resolve`、`budget_schedule_resolve`、`dmp_pack_resolve`、`material_pack_resolve`、`backup_landing_page_resolve` |
| 04 账户资源准备 | 头像、DMP、事件链、视频、产品图、品牌、小程序实例、备用落地页 | 各资源对应 `*_ensure` Skill |
| 05 草稿生成 | 项目名、草稿、字段合同、查重 | `project_name_reserve`、`payload_build`、`payload_contract_check`、`duplicate_check`、`create_readiness_check` |
| 06 创建执行 | execution grant、单次创建、对象 ID | `std_project_create_once` |
| 07 回查收口 | 对象状态、名称一致、字段一致 | `std_project_readback` |

工作台状态只显示：`passed` 为亮、`running` 为高亮描边、`waiting` / `blocked` / `failed` 为灰。API 返回已持久化的节点及子节点状态，前端只渲染，不编译业务判断。

## 4. Skill 与卡点定位规则

每个 Skill 需要在公共合同中声明：

```text
skill_key
node_key
input_contract
output_contract
stop_conditions
write_scope
module_ref
```

每次执行写入脱敏运行结果：

```text
status
blocker_codes
error_code
output_summary
module_ref
evidence_refs
attempt_no
started_at
finished_at
```

定位链路：

```text
job_id -> node_key -> skill_key -> 最新 skill run
-> blocker_code / error_code / module_ref / evidence_ref
-> 对应源码文件和函数
```

`scripts/` 只保留对 Skill 的 CLI、smoke 和 check 包装；业务实现只存在于 `src/workflows/skills/oe3/`。

## 6. 表职责与约束

| 表 | 职责 | 关键约束 |
| --- | --- | --- |
| `launch_jobs` | 一次对话对应的一轮完整创建 | 新对话必建新 job。 |
| `launch_node_runs` | 工作台 7 主节点状态 | `(job_id, node_key)` 唯一。 |
| `launch_skill_runs` | 子节点运行与卡点 | `(job_id, execution_cycle, skill_key, attempt_no)` 唯一。 |
| `launch_execution_plans` | 本轮自动执行计划 | 保存计划动作、阻断、`plan_hash` 与状态。 |
| `launch_confirmations` | 用户唯一一次确认 | 绑定 `job_id + plan_id`，只能消费一次。 |
| `platform_actions` | 所有真实平台动作审计 | `idempotency_key` 唯一；只保存摘要与 hash。 |
| `monitor_provision_runs` | monitor 最终状态 | 关联 job、plan、账户、游戏和路线。 |
| `monitor_provision_attempts` | monitor 创建尝试 | 每个 provision 最多两条。 |
| `account_resources` | 账户资源当前可用性 | 保存当前状态与必要平台 ID。 |
| `launch_drafts` | 最终可提交草稿 | `payload_hash` 稳定后才可创建。 |
| `created_objects` | 成功创建对象 | 一轮只允许一个 `std_project`。 |
| `readback_records` | 自动回查结论 | 保存最终状态和字段 diff 摘要。 |
| `evidence_artifacts` | 脱敏证据 | 不保存敏感原文。 |

## 7. 实施边界

- 代码中的节点与 Skill 元数据继续以 `src/workflows/skills/oe3/00-workflow-node-registry.mjs` 和 `00-contracts.mjs` 为唯一来源。
- Node 2 的 monitor 创建从“独立人工任务”调整为“统一 execution grant 下的自动子流程”，但仍使用单次动作、幂等键和回查。
- 未列入 `launch_execution_plan` 的真实平台动作必须停止执行，不得自行扩权。
- 旧 job 不重试；重新对话必建新 job。

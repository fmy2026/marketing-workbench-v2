# 工作流 7 节点与数据真值说明

更新时间：2026-08-27 CST

用途：给后续 Codex / 技术迭代快速理解 v2 当前工作流、文件归属、数据真值和权限边界。本文是稳定结构说明，不记录具体账户、monitor、token、Cookie、raw request、raw response 或完整 URL。

## 1. 当前结论

v2 当前是一套“通用工作台骨架 + OE3 路线 Skill 实现”：

```text
frontend/API
-> src/workflows/launchWorkflow.mjs
-> src/workflows/skills/oe3/00-workflow-node-registry.mjs
-> src/workflows/skills/oe3/00-runner.mjs
-> src/workflows/skills/oe3/01-07 Node Skill
-> src/platforms + src/repositories
-> Postgres marketing_workbench_v2.mwb
```

关键判断：

- 3 阶段 7 节点的编号、名称、阶段和输出元数据，唯一来源是 `src/workflows/skills/oe3/00-workflow-node-registry.mjs`。
- `00-runner.mjs` 是 OE3 Skill 编排入口；不再由多个文件各自维护节点定义。
- 一轮广告创建以 `mwb.launch_jobs` 为锚点。
- 运行过程分为 `launch_node_runs`、`launch_skill_runs`、`launch_drafts`、`platform_actions`、`readback_records`、`evidence_artifacts` 等可审计记录。
- Node 2 的乾坤 monitor bootstrap 已支持在 `planned_actions` mock 模式接入主 Workflow；`monitor:account-preflight` 可只读校验 `accountIndex` 并回写账户身份字段；真实乾坤 monitor 写入仍必须独立授权，不属于广告 job 的默认自动真实写入。
- Node 6 只有 execution grant 校验通过后才允许单次平台写入。

## 2. 文件归属规则

| 前缀 | 含义 | 示例 |
| --- | --- | --- |
| `00-` | 跨节点编排、公共合同、共享 CLI / smoke | `00-workflow-node-registry.mjs`、`00-contracts.mjs`、`00-runner.mjs` |
| `01-07-` | 对应 7 节点所属 Skill 或专项脚本 | `01-intake-normalize.mjs`、`05-payload.mjs`、`07-readback.mjs` |
| 无编号基础设施 | 按职责命名，不强行编号 | `src/platforms/`、`src/repositories/`、`src/server/` |

维护规则：

- 禁止新增第二份节点定义数组。
- 新 OE3 Skill 先在 `00-contracts.mjs` 声明 `nodeKey`，再由 `00-workflow-node-registry.mjs` 校验归属。
- 新 CLI / smoke 先判断属于 `00` 还是 `01-07`，不得新增无归属长期脚本。
- `package.json` 命令名是长期入口；底层 `scripts/` 文件可编号迁移，但不随意改命令名。
- `.archive/` 只作历史参考，禁止 runtime import、API route、package script 或 shell 调用。

## 4. Postgres 真值分层

| 分层 | 表 |

| 维度与配置 | `platform_routes`、`games`、`game_platform_apps`、`game_route_defaults`、`advertiser_accounts`、`account_touchpoints`、`game_assets`、`material_packs`、`material_pack_items`、`landing_page_assets`、`account_resources` |
| 单轮运行 | `launch_jobs`、`launch_node_runs`、`launch_skill_runs`、`launch_execution_plans`、`launch_drafts`、`project_name_reservations` |
| 执行与收口 | `launch_confirmations`、`platform_actions`、`created_objects`、`readback_records`、`evidence_artifacts` |
| Node 2 monitor bootstrap | `monitor_provision_runs`、`monitor_provision_attempts`、`qiankun_option_relations` |

约束：

- `launch_jobs` 是广告创建轮次锚点。
- `launch_node_runs` 记录 7 节点结果。
- `launch_skill_runs` 记录最小 Skill 单元。
- `monitor_provision_*` 是 Node 2 上下文 bootstrap 专项，可关联 `job_id + plan_id`，不是新的广告创建轮次体系。
- 普通表、API 和项目文档只保存脱敏摘要、hash、状态和必要 ID。
- raw payload、raw response、token、Cookie、secret、auth_code、完整 callback URL、完整点击监测 URL 不进入项目文件、普通日志、API 或前端。

## 5. Node 2 monitor bootstrap 边界

Node 2 有两种场景：

| 场景 | 行为 | 权限 |
| --- | --- | --- |
| 日常广告创建 job | 读取账户、monitor、触点、platform app 等上下文；已有 monitor 时不生成创建动作 | 默认允许只读 |
| accountIndex-only preflight | 只调用 `/tf/account_info/accountIndex`，用于验证凭据和账户身份字段 | 只读；禁止调用 monitor list 和创建接口 |
| 缺 monitor 的 planned action | `dry_run` 只做 `monitor-query/monitor-plan`；`planned_actions` mock 模式可执行 `monitor-ensure/monitor-readback` | 仅 mock transport，不真实写入 |
| 缺 monitor 的真实 bootstrap | 可能需要乾坤 monitor 创建/重试 | 必须另建任务、单次确认、低频执行、可回查，完成后收回写权限 |

注意：

- monitor bootstrap 已可作为 execution plan 的 Node 2 planned action 进入主链；真实写入仍不是广告项目创建的默认自动步骤。
- monitor 创建失败后的重试次数、目标账户和当前暂停状态属于动态状态，只看 `project.state.json`。
- mock server busy 场景遵守现有规则：间隔 5 秒、最多两次尝试，第三次停止。
- 不把一次性请求参数、响应原文或敏感凭据写入稳定文档。

## 6. Node 3/4 资源能力边界

Node 3/4 的资源 readiness 已收口到主 Workflow Skill 链路：

- 备用落地页 readiness 由 `03-landing-page-readiness.mjs` 统一判断，`scripts/03-*` 只调用同一 handler。
- Node 4 八项资源的 verify/prepare 能力由 `04-resource-action-registry.mjs` 唯一登记。
- 当前仅 `video_asset` 有已实现准备执行器：`src/platforms/oceanengineVideoMaterialExecutor.mjs`。
- 其他未就绪资源不进入可执行 `planned_actions`，只写 `resource_prepare_unsupported:<resource_type>`。
- 每个资源 Skill 输出统一包含 `resource_type`、`status`、`prepare_capability`、`blocker_codes`、`module_ref`、`evidence_refs` 和 `next_action`。

## 7. 后续 Codex 迭代检查清单

新任务启动：

1. 先读 `AGENTS.md`。
2. 再读 `project.state.json`。
3. 若 `active_task` 非空，按其 `read_order` 读任务卡和 manifest。

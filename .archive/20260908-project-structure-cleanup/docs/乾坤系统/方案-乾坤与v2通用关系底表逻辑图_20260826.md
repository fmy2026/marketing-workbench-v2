## 2. 当前结论

### 2.0 乾坤媒体三层模型

用户补充确认：乾坤“媒体渠道”是三层模型，不能把不同层级的字段直接互相校验。

| 层级 | 乾坤页面/概念 | 已知接口字段 | v2 当前理解 |
| --- | --- | --- | --- |
| 第 1 层 | 媒体系 | 页面页签“媒体系” | 近似对应 v2 `platform` |
| 第 2 层 | 媒体 | `selectList type=mediaList`；`accountIndex.media_master_id` | 媒体主体 |
| 第 3 层 | 媒体资源位 | `/tf/ad/index mediaId[]`；历史 monitor 的内部 `media_id` | 监测创建所需资源位 |

重要修正：

```text
selectList(mediaList) 是第 2 层“媒体”
/tf/ad/index mediaId[] 与历史 monitor media_id 是第 3 层“媒体资源位”
os=3 是乾坤“小游戏”技术系统类型，不单独决定业务媒体归属
```

所以，上一轮“历史 monitor media_id 与 mediaList.value 交集为 0”的结果，不能解释为“没有可用资源位”；它只说明第 3 层资源位 ID 不能直接拿第 2 层媒体列表校验。最新任务已改为直接验证第 3 层 `media_resource_id=310`。

## 3. 通用关系底表

`mwb.qiankun_option_relations` 是乾坤下拉、级联和可选项关系的唯一底表。一行只表达一条已观测或已确认的父子关系，不保存整份配置、raw response、token 或完整 URL。

| 字段组 | 字段 | 作用 |
| --- | --- | --- |
| 关系主键 | `relation_id` | v2 关系记录 ID |
| 业务作用域 | `route_id`、`game_code`、`os` | 指明这条事实用于哪条路线、游戏和技术系统 |
| 父项 | `parent_type`、`parent_id`、`parent_name` | 例如 `vest / 1414 / 巨兽战场` |
| 子项 | `child_type`、`child_id`、`child_name` | 例如 `package / 36820 / 36820` |
| 关系分类 | `relation_type` | 例如 `vest_to_package` |
| 证据状态 | `validation_status` | `observed / confirmed / stale / invalid` |
| 来源审计 | `source_endpoint`、`request_fingerprint`、`response_hash`、`evidence_artifact_id` | 只保留脱敏可追溯信息 |
| 时效 | `first_seen_at`、`last_seen_at`、`created_at`、`updated_at` | 判断关系是否需要重新核验 |

## 7. 重构原则

1. 保留现有 `qiankun_option_relations`，不再新增同义 option catalog 或 package/media 映射表。
2. 保留 `advertiser_accounts`，用其扩展字段保存当前账户技术身份，不另建 profile 表。
3. `game_route_defaults` 仅保留业务策略和 `reference_only` 候选；所有已验证技术关系必须来自 `qiankun_option_relations`。
4. `monitor_provision_runs` 与 `monitor_provision_attempts` 只记录一次生命周期与真实写入尝试，不能反向变成配置真值；L3 资源位只读验证只写 evidence 与关系底表，不覆盖创建失败事实。
5. 完整技术组合在各关系均核验通过前只作为运行时 DTO；是否新建最终配置表，应在技术组合真实完成后单独决策。
6. 前端仅消费状态、摘要、必要 ID、`touchpoint_ref` 与 `url_hash`，不展示 owner key、凭据、raw response 或完整触点 URL。
